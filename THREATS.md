# TrustVault threat model

## Scope and assets

This model covers the application: the React/Vite client, Express API, MongoDB records stored locally or in MongoDB Atlas, session cookies, permission records, audit events, and private Supabase Storage objects. It describes implemented server-side controls and their limits; it is not a production security certification.

Assets include account credentials, workspace membership, document metadata and bytes, permission grants, invitation codes, and audit history. Threat actors include unauthenticated callers, authenticated members of another workspace, viewers without a document grant, and members attempting operations outside their role.

## Security boundaries and controls

- The API verifies the signed HttpOnly session, compares its authentication version with the user record, and reloads the user's workspace membership from MongoDB for each authenticated request.
- Registration and invitation acceptance validate input and hash passwords with bcrypt before storing them. Login verifies the hash. Password hashes are excluded from normal user queries and API responses.
- State-changing requests require an `Origin` exactly matching `CLIENT_ORIGIN`; missing and untrusted origins are rejected. CORS allows credentials only for that configured origin (local default: `http://localhost:5173`). Non-browser callers have no origin-check bypass and must send the configured Origin and authenticate normally.
- Document reads, previews, downloads, permission changes, and deletes run in Express handlers. Document queries are scoped by the authenticated workspace; ownership comes from the document record, and sharing comes from active MongoDB permission records.
- Administrators can access documents in their workspace. A document owner can manage their own document. Other members require an unexpired, unrevoked view, download, or edit grant. Edit grants allow metadata edits and preview, but not download, deletion, or permission management; the workspace role remains unchanged. Download requires a download grant. The storage object is fetched through the API only after authorization, so a later request after revocation is checked against the new grant state.
- Viewers cannot upload, grant or revoke permissions, or delete documents. Workspace admins can remove members; their active document grants are revoked.
- Uploaded object paths are generated server-side and do not contain the supplied filename. The display filename is stripped of path separators and control characters. The API validates file signatures and restricts uploads to PDF, PNG, or JPEG up to 10 MB.
- Before upload, download, or delete, the server checks that its configured Supabase bucket exists and is private (`public: false`). Objects are never exposed with public or signed URLs; downloads are mediated by an authenticated API request with fresh authorization.
- Server handlers write audit events for document upload/view/download/edit/delete, permission grant/revoke, and denied access/permission attempts. Audit APIs are read-only; workspace-wide activity is admin-only and document activity is owner/admin-only.
- When authentication rejects a direct request to a document route, a per-IP limiter runs before any document lookup. Within the configured limit, requests naming existing documents produce denied audit events associated with that workspace and store no presented token. The default is 30 requests per 15 minutes; configure `UNAUTH_DOCUMENT_AUDIT_LIMIT` and `UNAUTH_DOCUMENT_AUDIT_WINDOW_MS` in the server environment. Requests for unknown documents cannot be assigned to a workspace and are not included in workspace audit views.
- Security integration tests use direct HTTP requests through Supertest and MongoDB Memory Server. Storage is a fake adapter in these tests.
- Database credentials come only from ignored `server/.env` or hosting secret settings. The connection helper accepts only `mongodb://` or `mongodb+srv://`, explicitly selects the `trustvault` database, uses a 15-second server-selection timeout, reuses an in-flight connection, and redacts MongoDB URIs from startup errors.
- Atlas access control remains an operator responsibility: use a least-privilege database user, a narrow IP access list, and TLS (provided by Atlas SRV connections). The automated tests do not verify these settings.

## Verified behavior and evidence

Run `npm test` for executable evidence of registration, bcrypt hashing and login, session revocation, CORS preflight, cross-workspace isolation, role restrictions, ignored client-supplied identity/role fields, denied direct view/download/delete/update requests, unauthenticated document-access audit events, permission levels, expiration, revocation on subsequent reads, private-bucket enforcement with a fake storage adapter, audit event creation, and read-only audit APIs. Run `npm run build` for the client production build. These checks do not validate a deployed service, live Supabase configuration, or a live MongoDB Atlas connection.

Live Supabase storage has not been verified. |
| Spoofed MIME, oversized upload, unsafe filename, or invalid category | Malicious/unsupported data, resource exhaustion, unsafe display metadata | 10 MB parser limit, signature/MIME agreement, filename sanitization, category enum validation, workspace-generated storage path | `uploads verified files, checks MIME and size, and serves downloads after authorization`; upload category is validated in the route | Signature checks do not detect malware; only PDF/PNG/JPEG are accepted. |
| Cross-site request forgery or origin-header omission | A browser may attach the session cookie to an unintended state-changing request | Every state-changing API method requires the exact configured `Origin`; missing and hostile origins are rejected before route handling | `CORS preflight and registration request errors return readable responses` (trusted, missing, and hostile origins) | This protects browser cookie requests; non-browser clients must provide the trusted Origin and valid session. Deployment must set `CLIENT_ORIGIN` to the exact frontend origin. |
| Edit-grant misuse | A named editor attempts to download, delete, grant access, or elevate their workspace role | Edit capability is checked from the current per-document grant; it is limited to metadata edits and preview. | Client fabricates audit events or mutates/deletes existing events | Loss or falsification of accountability | Events are written in server handlers; no audit mutation route exists; workspace activity is admin-only and document activity owner/admin-only | `records successful and denied access events and limits audit visibility`; `audits document edits with safe request context and exposes no audit mutation API` | MongoDB administrators or compromised server credentials can alter records. This is not tamper-proof storage; database and storage writes are not atomic. |
| Failed operation is recorded as successful | Misleading incident evidence | Success audit is written only after the corresponding operation succeeds; failures are separately reported/audited where implemented | `records document deletion only after the authorized deletion succeeds`; upload/download and permission event assertions in the named integration tests | Cross-service crashes can leave partial effects or missing events; reconciliation and external monitoring are operational responsibilities. |

## Known risks and limits

- No live MongoDB Atlas connection was verified during this change because no Atlas URI was available in the workspace. Tests use an isolated in-memory MongoDB. The operator must verify the Atlas URI, database user permissions, and IP access list.
- Any database password or JWT secret previously exposed outside its secure environment must be considered compromised. Rotate the Atlas password and JWT secret; changing `JWT_SECRET` invalidates all existing sessions. These rotations are not automated.
- Production MongoDB, Supabase, CORS, TLS, proxy, and cookie settings must be configured and verified by the operator. Create a private Supabase Storage bucket, then set backend-only `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `SUPABASE_BUCKET`; the server rejects buckets that Supabase reports as public. The service-role key bypasses Supabase Storage RLS and belongs only in the backend environment; never commit it or send it to the client.
- Integration tests replace Supabase with a fake adapter; they prove the application refuses a bucket reported as public, but they do not prove cloud IAM policy or live storage behavior. No live Supabase bucket was verified during this phase.
- File signature validation is not malware scanning. Only PDF, PNG, and JPEG are accepted.
- MongoDB and object storage do not share a transaction. A crash between storage, metadata, and audit operations can leave partial state; for example, a failed metadata deletion after object removal is reported and audited as a failure, but requires operator reconciliation. Audit-write failures cannot make two systems atomic.
- Registration creates one workspace per user in the current MVP. Invitation codes are bearer credentials and must be delivered to the intended email recipient over a trusted channel; no email delivery is implemented.
- Document metadata edits are available to the owner, administrator, or explicitly granted editor. Download requires the owner/admin or a download grant. Document deletion and downloads are mediated by the backend, which buffers files up to the configured size limit.
- A successful local test suite is not evidence of a production deployment or of protection against infrastructure compromise, compromised administrator accounts, or malicious files.

## Audit integrity limits

The application exposes audit events through read-only routes and enforces workspace administrator access for workspace-wide activity. This is not tamper-proof storage: a MongoDB administrator or compromised server credential can change or delete records, and ordinary backups do not independently establish event integrity. Stronger assurance requires a separately controlled append-only/WORM destination, restricted database roles, backups, and external integrity monitoring. Audit writes and document/storage changes cannot share an atomic transaction; a failure between systems can leave partial state, which should be reconciled operationally.
