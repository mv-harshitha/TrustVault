# TrustVault — five-minute demo script

## Before the demo

- Use the deployed [TrustVault frontend](https://trust-vault-ecru.vercel.app/) and three disposable test identities in a dedicated demo workspace.
- Create the administrator account first, then invite separate `owner` and `viewer` identities. Invitation codes are single-use bearer secrets: share them privately with the matching test identity and do not include them in slides, chat logs, or recordings.
- Prepare a synthetic PDF or image containing invented text only. Do not upload personal, confidential, or production documents.
- Confirm that the test accounts can sign in. The app does not send invitation emails; an admin must copy each code from the UI.

## Walkthrough

| Time | Presenter action | What to explain |
| --- | --- | --- |
| 0:00–0:30 | Open the frontend and introduce TrustVault. | It is a React/Vite client backed by an Express API, MongoDB metadata, and private Supabase object storage. The backend—not hidden UI controls—enforces roles and document grants. |
| 0:30–1:15 | Sign in as the Administrator and show the workspace and member list. | Registration creates the workspace's first administrator. The administrator can invite workspace members, but invitation codes must be delivered out-of-band and expire after 48 hours. |
| 1:15–2:00 | Sign in as the Document Owner, upload the prepared synthetic file, and open its details. | The owner can upload and manage their own document. The server validates file type/size, stores a generated object path, and writes audit events. The actual file content is held outside MongoDB in private storage. |
| 2:00–2:45 | Grant the Viewer named `edit` access to the document. Sign in as the Viewer and open/preview it; change its name or category. | An `edit` grant allows metadata changes and preview. It is per-user, scoped to the workspace/document, and rechecked by the API on each request. |
| 2:45–3:30 | As Viewer, try to download the document; show that this is not granted. If appropriate, show that delete and permission-management controls are unavailable. | `edit` does not imply `download`, deletion, permission management, ownership, or administrator privileges. Authorization must still hold for direct API requests. |
| 3:30–4:15 | Return as Owner and revoke the Viewer grant. Sign back in as Viewer or refresh, then try to access the document again. | Revocation is checked on the next request; this does not recall bytes already downloaded or a request already authorized and in progress. |
| 4:15–5:00 | Sign in as Administrator and show workspace audit activity. Close with the security boundaries and limits. | Events are generated by trusted backend operations and exposed read-only through the app. The audit store is not tamper-proof against database/server administrators. Production health was checked, but this demo—not the health endpoint—is what exercises actual user flows. |

## Demo safety and limitations

- Use unique, disposable passwords and test-only email addresses you control. Never show or share passwords, JWTs, environment variables, service-role keys, or invitation codes.
- A health response only shows the API is serving. Do not claim production storage, authorization, or audit behavior was verified unless the corresponding demo actions succeed.
- The MVP has no workspace/account deletion flow. Test documents can be deleted by an owner/admin and members can be removed by an administrator, but the demo workspace and account records may remain. Avoid creating demo accounts unless you accept that persistence.
- For a view-only comparison, revoke edit and grant `view`; preview is allowed, while editing and download are not. A `download` grant is separate from both `view` and `edit`.
